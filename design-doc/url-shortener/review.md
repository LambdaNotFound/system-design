# Review ledger: url-shortener

## Round 1

11/15/26. Derivation, written from the brief before opening the design:

- Invariants: one code maps to one stored URL forever (FR5, NFR7); one FR4-normalized URL maps to at most one returned code, decided by a single linearization point that concurrent first submissions race on (FR3); the code row must be durable in two regions before the code is returned (NFR6), and readable by every redirect server at that moment (NFR11), which rules out async replicas and any negative cache that can outlive a create.
- Hard constraints: 1,157 creates/s and 11,574 redirects/s average, 10x peak (NFR1); 365 billion rows (NFR2); codes of at most 8 characters that can't be predicted (NFR8, NFR12): 62^7 = 3.5 trillion is 10.4% full at 365 billion, 62^8 = 218 trillion is 0.17% full, so random 8-character codes rarely collide; disable reaches every cache within 5 minutes (FR6), which bounds every cache TTL and the HTTP max-age together.
- Minimum moving parts: stateless API servers; a sharded, strongly consistent, multi-region store with two keyed tables, code to URL and hash of normalized URL to code, each with conditional insert; write the code row first so a crash leaves only an unreturned orphan; a redirect cache with a TTL bounded by FR6 and no negative entries that survive a create; per-IP counters for FR8 and NFR8 that fail open so they can't take down NFR4.
- Seams to probe: the two-table write and its crash window (FR3, NFR7); NFR11 against any cache, CDN or async replica; NFR8 cool-off against any edge cache that answers before the counter is consulted; FR9 disabled-URL check on the dedup path; how per-IP counting handles IPv6 and proxies.

Diff against the design: it reaches the same place as the derivation by a stronger route (one serializable transaction for both inserts instead of code-row-first ordering, a bounded-staleness local read with a consistent fallback, positive-only caching). The estimates recompute (rates, 62^8 density, 59.9 TB and 299 TB, 3.85 PB, 124 TB, 3.05 × 10^8 pairs, 5.8 × 10^-55, S + T + M = 150 s, 1,029 probes and 1.7 hits a day). The FR and NFR tables match the brief verbatim; every row is served in Proposed Solution or Work Breakdown; the brief has no LLD rows. Word count 3,996 of 4,000; no dashes; no `path:line` above the marker. Where it departs from the derivation is the regional scope of the abuse controls and the edges of the read path's fallback.

R1-1 | blocking | NFR8 requires that an IP over the miss limit has every lookup rejected for the cool-off, but the cool-off set lives in a regional counter store and servers pull only their own region's set, so an IP cooled off in one region is served normally in the other two (and by any server whose counter store has fallen back to in-process counters). The stated kill reason, that a global counter puts a cross-region write on every miss, applies to the counters, not to the cool-off set, whose entries start rarely. | Make the cool-off itself service-wide (counting can stay regional), or show why it can't be and take the gap to the user as a brief correction to NFR8; say what the in-process fallback does to the cool-off set; update the Appendix's three-region yield to match.
R1-2 | should-fix | Failure analysis of step 4: the F = 64 bound is shared by unknown codes and fresh codes, so a botnet that keeps step 4 saturated in a region turns every just-created code's lookup there into a `503`, which breaks NFR11 (and spends NFR4) for legitimate links, not only for the enumerator. The "A botnet enumerates" bullet names only the miss rate. | State the miss rate per region at which fresh-code lookups start failing, and either a mechanism that keeps fresh codes resolvable under it or the gap stated as a residual risk against NFR4 and NFR11.
R1-3 | should-fix | "The store is slow" says slowness costs uncached lookups only, but a local replica slower than step 3's 20 ms timeout sends every uncached lookup, live codes included, to step 4, where F caps it and the rest get `503`. The bullet never sizes the uncached share of redirects, nor says whether the sentinel health check fails and drains the region in that state, so the "slow" answer for the hot path's main dependency is unbounded. | Size the uncached share (cache hit rate assumption) and state what a slow local replica does to NFR4: drain, shed, or the failure fraction it accepts.
R1-4 | should-fix | NFR4's 99.99% (about 52.6 minutes a year) has no recovery-time arithmetic: a partitioned region serves `503` for every uncached lookup once S passes, until health checks fail and client DNS caches expire, and neither the health-check interval and threshold nor the DNS TTL is stated. | State the detect-and-drain time for a region failure and a partition, and how many such events fit NFR4's budget, or name it as an assumption to measure.
R1-5 | should-fix | Steel-man: the DynamoDB MRSC rival is rejected for needing a pending-claim protocol with a repairer, but its advocate would write the code item first with a conditional put, then conditionally put the URL key: a crash or a lost race leaves only an unreturned code item that redirects to an FR4-equal URL, so NFR7 holds with no pending state and no repairer (the real wart is that such an orphan isn't covered by the winner's disable). Meanwhile the con that likely does kill it goes unnamed: per the cited page, DynamoDB offers no bounded-staleness local read, so either FR6's S bound or NFR3's in-region read is lost. The store is a ten-year one-way door, so the kill reason has to be the real one. | Restate the rival in its steel-manned form and give the con that actually decides it, citing the requirement it breaks.
R1-6 | should-fix | The keyed-permutation rival's con says a reissued counter range "breaks NFR7", but `links.code` is a primary key, so a reissued value fails as `CodeTaken` rather than misdirecting; likewise rotating the key collides only at random-code rates and retries the same way. The con names a failure the design's own schema prevents. | Replace it with the rival's real costs (a durable counter to operate, a secret to guard for ten years) set against random codes' rare retry.
R1-7 | should-fix | Canonicalizer step 1 runs every host through UTS #46 ToASCII, which maps case, yet the Example stores `HTTPS://Example.com:443/a/../b` as submitted and FR2 redirects to the URL exactly as submitted. Either ASCII hosts are lowercased in storage (contradicting the Example and FR2) or ToASCII runs only on non-ASCII input (unstated). | Say when ToASCII runs, matching FR10's trigger, so the stored spelling and the Example agree.
R1-8 | should-fix | Repetition at 3,996 of 4,000 words, with fixes still to come: the Estimates "Disable budget" bullet and the Redirect Resolver's "Staleness (FR6)" paragraph both derive the 90 s and 150 s bounds, and the Overview's last three sentences restate the Disables, Partitions and Latency paragraphs. | Keep the arithmetic in Estimates and point to it from Staleness; cut the Overview's restatements to a pointer.
R1-9 | nit | The Disable Tracker is a singleton with no failure mode: if it stops, NFR9's per-disable timing and the 90 s page silently stop. | One line in Failure Modes, or a metric for tracker liveness.

Spot-checks: scoping.md :85, :86, :90, :91, :93, :95, :96 held; CockroachDB survival goals (3 regions, 2+2+1, write latency at least the nearest RTT, available through a region outage) held; Follower Reads (local reads under partition, increasingly stale; `nearest_only` errors; single-row implicit transaction; at least 4.2 s) held; DynamoDB MRSC (exactly three regions, RPO zero, transactions unsupported, conditional writes on the latest version) held; arithmetic rows (rates, code space, storage, both collision figures, FR6 budget, enumeration yield) held on recomputation.

Verdict: revise

## Round 2

11/16/26. Standing derivation, carried from Round 1 unchanged (no amendment in the brief; no rebuttal moved it):

- Invariants: code to URL is write-once (FR5, NFR7); one FR4-normalized URL maps to at most one returned code through a single linearization point (FR3); a code is durable in two regions before it is returned (NFR6) and resolvable by every serving server at that moment (NFR11), so no negative cache may outlive a create.
- Constraints: 1,157 creates/s and 11,574 redirects/s average, 10x peak (NFR1); 365 billion rows (NFR2); 8 random base62 characters, 0.167% full (NFR8, NFR12); S + T + M within FR6's 300 s.
- Minimum parts: stateless servers; a sharded, strongly consistent multi-region store with conditional inserts on code and URL key; a positive-only bounded cache; per-IP counters that fail open, with an NFR8 cool-off that holds on every lookup path, in every region.
- Seams for this round: the revised cool-off path (`GLOBAL` table, poll, fallback); the step 4 slot split and its clean/dirty classification; the drain arithmetic against NFR4; the new health-endpoint trigger; repetition and word count after the additions.

Diff against the design: R1-1 to R1-9 are answered as accepted and the text matches each response. The FR and NFR tables still match the brief verbatim; word count 3,998 of 4,000; no dashes or `path:line` above the marker. The revision's new seams are the cool-off's path from a regional count to a rejection on every server, and the identity the counts key on.

R2-1 | blocking | Revised material (R1-1's cool-off path, R1-2's slot split). The Appendix bounds a prober at 150 probes per 70 minutes and 5.2 live codes a day, but nothing rejects an IP between its 50th counted miss and the moment the `cooloffs` row reaches each server's 1 s poll after `GLOBAL` commit-wait: step 1 checks only the polled set, though step 4 already reads the regional count. Worse, a lookup shed at step 4 with `503` is not counted as a miss, while step 3 still answers its live hits, so one fast prober pinned to one server fills the 16 shared slots alone and keeps probing uncounted. Yield then scales with the prober's request rate times the propagation gap, not with the 50-miss limit, and with fast probes the cycle is about 60 minutes, not 70. | Reject at step 1 once the regional count passes the limit, and apply a written cool-off on the writing server at once; count a step 4 shed of a locally absent code from an IP with misses as a miss, or put a per-IP lookup rate in front; then restate the Appendix bound with the probe rate it assumes.
R2-2 | blocking | Missed and critical. Edge and client identity counts IPv6 by /64 as "a subscriber's usual allocation" (Evidence: assumed, from memory). RIPE-690 recommends a /48 or /56 per end user and says assigning a /64 or longer does not conform to IPv6 standards, so one residential subscriber holds 256 identities and one business or tunnel-broker user 65,536. That multiplies FR8's 100 an hour and NFR8's per-cycle miss allowance by the same factor for a single caller, and puts the 576,000 identities that saturate step 4 within reach of a few /48s on one host. Scoping left IPv6 handling to the design and accepted only that one IP is roughly one caller; /64 breaks that premise. | Key IPv6 counts on the prefix one caller holds (a /56, or limits at /64, /56 and /48 with wider prefixes getting higher thresholds), cite the source for the choice, state the shared-quota cost of the wider prefix, and redo the Appendix yield and the botnet bullet with it.
R2-3 | should-fix | Revised material (R1-3). The new health trigger, over 5% of step 3 reads timing out in 10 s, is load-sensitive, and a drain moves a third of the traffic onto the other two regions' replicas, raising their step 3 load by half; a slowdown caused by load, such as NFR1's 10x peak, can then trip them in turn. The design states no headroom per region for a drained region's share, which "A region fails" also needs. | State the per-region headroom the drain assumes, and what ends a cascade: Route 53 treats every record as healthy when none is (Evidence), so name that fail-open as the floor, or trip the timeout trigger only on a regional signal or the sentinel.
R2-4 | should-fix | Repetition: the Estimates "Availability budget" bullet re-derives the Appendix "Availability per region drain" item (3,154 s, 120 s, 40 s, 78 a year); the spec says the body never repeats the Appendix. At 3,998 of 4,000 words, R2-1 and R2-2 need the room. | Keep the result and a pointer in Estimates, and the arithmetic in the Appendix only.

Closed: R1-1 resolved (cool-offs are service-wide; their propagation edge is R2-1); R1-2 resolved (repeat probers confined to 16 slots, wide-botnet residual stated); R1-3 resolved (uncached share sized, slow replica drains; its cascade is R2-3); R1-4 resolved (drain arithmetic recomputes: 3,153.6 s, 40 s an event, 78 a year, conservative since failures start at S); R1-5 resolved (steel-manned rival; the staleness con also holds against an eventual-then-strong tiered read); R1-6 resolved; R1-7 resolved; R1-8 resolved; R1-9 resolved.

Spot-checks: Route 53 health-check row (10 s or 30 s interval, consecutive-check failure threshold, 18% rule) held, page read 11/16/26; DynamoDB MRSC rows (synchronous to at least one other Region, strongly consistent reads and writes need cross-Region communication, no `ReplicationLatency` for MRSC, eventually consistent reads permitted in the FIS note, transactions unsupported) held, page read 11/16/26; IPv6 /64 row failed against RIPE-690 (https://www.ripe.net/publications/docs/ripe-690/, read 11/16/26), so the sample was widened; arithmetic rows (7,733 a second, 1,280, 960, 576,000, 3,154 s, 40 s, 78, 3,086 probes and 5.2 codes a day) held on recomputation, though the 5.2 model fails per R2-1; FR and NFR tables verbatim and word count held.

Verdict: revise

## Round 3

11/16/26. Standing derivation, carried from Round 2 unchanged (no amendment in the brief; no rebuttal moved it):

- Invariants: code to URL is write-once (FR5, NFR7); one FR4-normalized URL maps to at most one returned code through a single linearization point (FR3); a code is durable in two regions before it is returned (NFR6) and resolvable by every serving server at that moment (NFR11), so no negative cache may outlive a create.
- Constraints: 1,157 creates/s and 11,574 redirects/s average, 10x peak (NFR1); 365 billion rows (NFR2); 8 random base62 characters, 0.167% full (NFR8, NFR12); S + T + M within FR6's 300 s.
- Minimum parts: stateless servers; a sharded, strongly consistent multi-region store with conditional inserts on code and URL key; a positive-only bounded cache; per-caller counters that fail open, keyed on the address block one caller actually holds, with an NFR8 cool-off that rejects from the limit onward on every lookup path, in every region.
- Seams for this round: R2-1's revised rejection path (step 1 regional check, local cool-off, shed-as-miss, per-IP rate) and the restated Appendix bound; R2-2's IPv6 prefix keying and its yield and botnet arithmetic; R2-3's headroom and cascade floor; R2-4's cut; word count after the additions.

Diff against the design: R2-1 to R2-4 are answered as accepted and the text matches each response (design.md unchanged since commit 0f479ab). Step 1 now rejects on the regional count, so the propagation gap no longer sets the yield; identities at /64, /56 and /48 cap a /48 holder at 16 times; regions are sized for half the peak and the Route 53 fail-open is named. FR and NFR tables verbatim; word count 4,000 of 4,000; dashes only inside SQL comments; no `path:line` above the marker. What remains is in the new arithmetic's inputs and the costs of the two new rules: shed-as-miss and prefix-wide cool-offs.

R3-1 | should-fix | Revised material (R2-1). The Appendix's overshoot r × ℓ uses ℓ = 10 ms, but a miss is charged only when its lookup ends, and a lookup of an absent code runs step 3 (up to 20 ms) and then step 4, which the design's own Evidence puts at 50 ms. So ℓ is about 70 ms, the overshoot is 70 per region at r = 1,000, not 10, and the yields are 3 × (50 + 70) × 24 / 598 = 14.4 live codes a day for an IPv4 address (not 7.2) and 104.7 for a /48 holder (not 97.5). "Whatever the probe rate" also needs its real bound: once the IP is dirty, in-flight step 4 lookups are capped by its 16 shared slots per server, so the overshoot is at most min(r × ℓ, 16 × servers the prober reaches), which grows with fleet size. No sizing rests on the figure, so not blocking. | Take ℓ from steps 3 and 4 as specified (or say why a miss is charged before step 4 ends), state the overshoot as min(r × ℓ, 16 × servers per region), and redo the two yields and their Evidence row.
R3-2 | should-fix | Revised material (R2-1's shed-as-miss rule). A step 4 timeout or shed of a locally absent code now counts as a miss, so under a slow leaseholder, a partition before S, or a botnet saturating step 4, a legitimate client that opens many fresh links (a chat or social link unfurler is exactly that pattern) passes 50 in 10 minutes on codes that exist, and gets a 1-hour service-wide cool-off that also rejects its live, cached codes after the event ends. NFR8's cool-off is for codes that do not exist, and FR2 promises redirects outside it. "The store is slow" still says a slow leaseholder "costs fresh and unknown codes only", which the charge makes false; the botnet bullet names the charge but not the hour-long tail. Counting a shed is still needed, since a `503` leaks "absent locally" as well as a `404` does. | State the cost in the slow-store and botnet bullets (who gets cooled off, for how long, and that NFR4 counts their `429`s as available so no burn-rate alert fires), and either accept it as a residual risk with a trigger metric (cool-offs started by shed charges) or narrow it, for example by charging sheds to the step 4 slot class only, or only from an identity that already has a confirmed miss.
R3-3 | should-fix | Revised material (R2-2). The design prices the quota a wider prefix shares, but not the cool-off's blast radius: one prober's 800 misses cool off its whole /48 for an hour, in every region, on every lookup. RFC 6459 gives each phone its own /64 and says nothing of how carriers lay them out (the design's own Evidence row marks the packing assumed), so one phone on a carrier's /48 may cut redirects for up to 65,536 subscribers, repeatably each hour, and NFR4 counts those rejections as available, so no availability alert fires. The text names only "phones packed into one /56 share 4 times one caller's", the quota side, at /56. The prefix-wide rejection is needed against a home /48 holder rotating its /64s, so this is a cost to state, not a mechanism to drop. | State the cool-off blast radius at /56 and /48 with its trigger (a metric of lookups rejected per cool-off identity, paging on a /48 or /56 cool-off whose rejected volume spans many /64s), or narrow what a wider-prefix cool-off rejects for /64s that had no misses of their own, and say which NFR8 protection that gives up.
R3-4 | nit | The Abuse Limiter says step 1 "rejects once any passes 50", while the limits are 50, 200 and 800 by prefix; the step 1 sketch's "past its regional miss limit" is right. | "once any passes its limit".

Word budget: the RFC sits at exactly 4,000 words, so R3-1 to R3-3 have to be fitted by cuts; the Overview's caveat sentence and the Estimates "Availability budget" pointer are candidates.

Closed: R2-1 resolved (step 1 rejects on the regional count, sheds are charged; its overshoot input is R3-1, its cost R3-2); R2-2 resolved (identities at /64, /56 and /48 per RIPE-690 and RFC 6459, yield and botnet redone; the cool-off blast radius is R3-3); R2-3 resolved (half-peak sizing, sentinel timed, Route 53 fail-open named as the floor, confirmed against the page); R2-4 resolved (Estimates carries the result and a pointer only). R1 objections stay closed; no regression found.

Spot-checks: RIPE-690 row (/48 business, /56 residential, longer than /56 strongly discouraged, /64 or longer does not conform, a /64 per PDP context for phones, §1 and §4.2.2 to §4.2.4) held, page read 11/16/26; RFC 6459 row (unique /64 per default bearer, §3.2, §5.2) held, and the RFC is silent on carrier layout within a /56 or /48, so the "packed" row's assumed label is correct; Route 53 "if no record is healthy, all records are healthy" held, page read 11/16/26; arithmetic rows (38,667 share, 58,000, 11,600, 1,280, 960, 576,000, 3,154 s, 78, 4,320 and 7.2, 58,320 and 97.5) held on recomputation, with the ℓ input failing against the design's own step 4 figure (R3-1); FR and NFR tables verbatim, word count 4,000, no dashes or `path:line` above the marker held.

Verdict: revise
